# ผลการพิจารณาจาก ผอ.

ผู้ส่งเรื่องผ่าน approval_flow จะถูกระบุด้วย sent_uid เพิ่มจาก sent_pid เพื่อให้ไอดีหลักที่ไม่ผูกบุคลากรได้รับกระดิ่งผลอนุมัติด้วย ครอบคลุมพัสดุ การเงิน ธุรการ โครงการ และอาหารกลางวันที่ใช้แกนอนุมัติกลาง

เมื่ออนุมัติหรือส่งกลับแก้ บันทึกผลสำเร็จก่อนส่งอีเมลผ่าน BackgroundTasks ใช้อีเมลในทะเบียนบุคลากรของผู้ส่งก่อน ถ้าไม่มีใช้อีเมลที่เป็นชื่อบัญชีเข้าสู่ระบบของผู้ส่ง ต้องตั้ง SMTP จึงส่งจริงได้ บัญชีที่ไม่มีทั้งสองอย่างจะเห็นผลในกระดิ่งแทน อีเมลส่งไม่สำเร็จไม่ย้อนผลอนุมัติ ไม่อ้างว่าส่งอีเมลสำเร็จในหน้าจอ และไม่มีระบบส่งซ้ำอัตโนมัติในรอบนี้

อีเมลไม่ส่งสำหรับรายการที่อนุมัติไม่สำเร็จหรือกดซ้ำ การอนุมัติหลายเรื่องตัด ID ซ้ำก่อนทำรายการ และส่งเฉพาะผลที่ commit สำเร็จ อีเมลแสดงข้อความผู้ใช้แบบ escape HTML

คลิกกระดิ่งผลอนุมัติที่ /approvals/result/{id} ทำเครื่องหมายอ่านเฉพาะบัญชีผู้ส่งและเปิดหน้าผลของเรื่องนั้น ข้อมูลยังแยกฐานข้อมูลตามโรงเรียน ไม่รับ UID ผู้ส่งจากฟอร์ม ใช้ session เท่านั้น

รายการเก่าที่ยังรอพิจารณาและไม่มี sent_uid จะจับคู่บัญชีที่ active ในโรงเรียนเดียวกันด้วย person_id หรือชื่อผู้ส่งที่ตรงกับ display_name เพียงบัญชีเดียว หากชื่อกำกวมจะไม่เดาบัญชี บุคลากรเดิมยังได้รับแจ้งแบบเดิมเมื่อระบุบัญชีไม่ได้ ผลเก่าที่อนุมัติแล้วไม่ส่งอีเมลย้อนหลัง

เพิ่ม sent_uid INTEGER และ result_read_at DATETIME แบบ nullable ผ่าน migration ปกติ คงประวัติอนุมัติและรูปลายเซ็นเดิม

## ขอบเขตลายเซ็น

แกนอนุมัติกลางแปะลายเซ็น ผอ. เฉพาะขั้นและเอกสารที่อนุมัติแบบแปะลายเซ็น การอนุมัติอย่างเดียวจะติ๊กอนุมัติและเว้นการลงนามด้วยมือ เอกสารพัสดุ/การเงิน/อาหารกลางวันไม่แปะลายเซ็นเจ้าหน้าที่หรือกรรมการทุกคนอัตโนมัติจากการกดของ ผอ. เอกสารใบลา/ไปราชการและธุรการบางชนิดมีการแปะผู้ขอ/ผู้จัดทำตามวิธีเดิม ไม่เปลี่ยนวิธีลงนามบุคคลอื่นในการแก้รอบนี้

## ตรวจสอบ

ทดสอบการอนุมัติพร้อม/ไม่พร้อมลายเซ็น การส่งกลับ HTML escaping บัญชีเจ้าของไม่ผูกบุคลากร การอ่านกระดิ่งเฉพาะผู้ส่ง การจับคู่ข้อมูลเก่าแยกโรงเรียน การส่งหลายเรื่อง การส่งซ้ำ และ SMTP ล้มเหลวโดยจำลองบริการอีเมล ไม่ส่งอีเมลจริงในการทดสอบ ตรวจไฟล์ Word ว่ามีรูป ผอ. และไม่มีรูปเจ้าหน้าที่ที่อัปโหลดไว้ และตรวจปุ่มบนหน้าจอคอมพิวเตอร์ แท็บเล็ต และมือถือ
